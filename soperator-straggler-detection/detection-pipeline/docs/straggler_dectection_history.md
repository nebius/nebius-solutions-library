Purpose of this document: the narrative companion to the technical plan doc (v11) and the codebase reference. This covers why things are the way they are — every real bug found, every dead end ruled out, every design decision and the evidence behind it — from the very first feasibility question to where the project stands today. If the plan doc is the map, this is the story of how it got drawn.

Phase 0 — The question and the setup
The project began with one question: can a straggler GPU (a machine that's slow, not dead) be detected automatically, during a live distributed training job, without touching customer code?

A personal 2-node × 8×H200 Soperator cluster was deployed (Terraform → Flux → Helm) to have real hardware to test against — including working through a CRD schema mismatch and node CPU sizing issues just to stand the cluster up.

Phase 1 — Feasibility study
The first real finding was the detectability gradient: platform telemetry sees hardware and host-level causes clearly, sees network faults only from the provider side (never attributable to a specific tenant), sees storage faults weakly (masked by page cache), and is completely blind to data-pipeline faults. This gradient shaped every design decision downstream.

Key design principles established here, all of which held up for the rest of the project:

Two detection modes are needed, not one: peer comparison (catches localized compute/host faults) and baseline drift (needed for network, since a network fault hits every rank roughly uniformly and peer comparison can't see uniform effects).

Percentiles, not whole-run means — a fault that only runs mid-job gets diluted below any threshold if you average the whole run.

GPU utilization lies — during a network stall, GPU utilization reads 100% because NCCL waiting counts as busy. A naive detector watching utilization alone would see green lights on a crippled job.

The comm-sink rule — high communication time on many ranks usually means someone else is slow, not that the network is bad. Look for the one rank with an anomalous non-communication bucket first.

Phase 2 — Choosing the measurement tool: Inspector vs. CoMMA
Two NCCL profiler plugins were compared head to head. Inspector won decisively — 27.44x arrival-lag separation vs. CoMMA's 1.048x on the identical injected fault, a 57x gap relative to Inspector's own noise floor. The root cause: Inspector calls gettimeofday() fresh on every event (self-correcting); CoMMA reads the clock once at startup and extrapolates forever (any calibration error is permanent). This was proven with a real, decisive experiment (swapping which physical machine hosted which ranks, and watching the offset follow the rank numbers, not the hardware).

Two real bugs were found in NVIDIA's shipped code along the way: a filed SIGBUS bug in NCCL's plugin loader (NVIDIA/nccl#2367), and an unfiled single-slot buffer overflow in Inspector itself that silently dropped records at high collective density (fixed with a 241-line ring-buffer patch).

Phase 3 — Building the classification engine
The core detection mechanism, unchanged and foundational for the entire rest of the project: at a barrier, early arrivers wait inside the collective and show long exec times; the straggler arrives late, doesn't wait, and shows the shortest.

Three statistics were built, each mapped to a different fault shape: mean for sustained faults, CV for frequent intermittent bursts, outlier count for rare bursts. A separate, cause-metric-first check was built for whole-node host faults (CPU-based, not arrival-lag — arrival-lag-based host detection was tried first and achieved a 0% detection rate before being rebuilt from scratch), and another for network faults (IB counter-based).

The classification engine was hardened through seven rounds of deliberately adversarial testing, each round finding and fixing a real bug: stale cause-metric timing, outlier misattribution on whole-node faults, network detection being maskable, a network-bound-collectives blind spot for compute faults (documented as physics, not a bug), state never aging out of CONFIRMED, rank-0's CV threshold being fundamentally unworkable (twice), and the rank-15 anomaly (traced to ring position, not physical hardware — a lesson that recurred multiple times later in the project in new forms).

The strongest single piece of validation in this whole project happened here: a real, unplanted hardware fault (GPU 3, degraded to ~51% throughput) was detected unprompted, at a z-score nearly identical to the synthetic fault used to validate the method. This is the proof the whole approach works on real problems, not just injected ones.

Phase 4 — Wiring to live metrics
The pipeline was built end to end: Inspector → node_aggregator.py (per-node, computing statistics live) → VictoriaMetrics → the classifier. Key findings: PromQL can't natively express CV's trim step (so a companion Python computation layer is required, not pure PromQL); emission cadence has to be workload-adaptive (a 4.3x spread was measured between two workloads' natural collective rates); in-plugin aggregation was investigated and correctly ruled out (no cross-rank primitive exists inside the NCCL plugin); and VictoriaMetrics dedup was found to destroy the data at default settings — a 30-second dedup window loses over 90% of the samples this pipeline needs, since CV's persistence window is entirely inside one dedup bucket. This dedup problem recurred and had to be re-solved multiple times throughout the project (see the routing section below).

RAS (ncclras) was added as a separate, near-zero-cost fail-stop layer — genuinely different from everything else, since it catches a rank dying, not slowing down.

Phase 5 — Continuous-run hardening (P20a/P20a.5)
The first multi-hour continuous run found a real windowing discrepancy: the live aggregator's windowing was only an approximation of the reference classifier's exact windowing (a wall-clock sliding buffer vs. a strict sample-count-synchronized partition), producing 77 false fires vs. the reference's 43 on identical data. Fixed exactly, then a real, nonzero base-rate false-positive effect was found and reduced to zero across 177 minutes via a combined threshold change (CV z-threshold 20→60, persistence tightened to 3 consecutive windows).

This "zero" result later turned out to be a real, important overstatement — see P20d below.

Phase 6 — Dashboards, alerting, and the first full validation
The Grafana dashboard was built with two fault-injection-validated panels (a cross-rank statistical relationship panel, and a coverage/data-quality panel) and one intentionally-stubbed panel (network), pending a datasource-routing decision.

The alerting layer was built with a severity split — CONFIRMED pages a human, PROBABLE/UNCONFIRMED just logs. This turned out to be one of the most important design decisions in the whole project, because of what came next.

P20d — the first real blind end-to-end validation — found the false-positive rate estimate from P20a.5 was wrong. A genuine 3-hour blind test found a real PROBABLE-tier false-positive rate of ~22-38/hour (settling around ~32/hour across three independent runs), not the earlier "~0." This mattered enormously less than it could have, precisely because the severity split had already been built — every one of those false positives was correctly capped at LOG-ONLY, never a false page. The lesson: the severity split, built for a different reason, turned out to be the thing that made an unexpectedly-high noise rate a non-event instead of a crisis.

The same investigation also found and fixed a real bug where mean had never actually worked at all. Its "worst rank" selection logic (max() of exec times) could structurally never select a real straggler, because this project's own barrier mechanism guarantees a straggler shows the shortest time, not the longest. This had been silently broken since the beginning — the historical GPU-3 detection (z=217.9) almost certainly came from a different, offline analysis method, not this exact code path. Fixed by switching to largest-absolute-deviation-from-median, direction-agnostic. In the same investigation, a ~16x real, completely invisible job-wide throughput collapse was found — nothing in the system, at any level, could see a uniform slowdown across all ranks. A new detector (uniform_slowdown) was built specifically to close this.

A separate, very dangerous incident occurred during this stretch: node_aggregator.py ran for over three hours with a misconfigured push URL, computing real data locally the whole time but pushing none of it — producing a clean-looking "0 alerts" log completely indistinguishable from a genuinely healthy run. This led to building a dead-man's-switch: a heartbeat pushed independently of training data, checked unconditionally every poll cycle. Building this fix itself surfaced two more real bugs (a timestamp bug that would have made the health check blind for up to 5 minutes, and a threshold sitting inside normal healthy oscillation) — both caught only by testing the checker against live data.

A related timestamp bug (value[0] — query evaluation time — being used where the real sample timestamp was needed) was later found to affect every single rank-based statistic in the alert engine, not just the dead-man's-switch. This class of bug recurred at least three separate times across the project in different files, always found by the same method: testing against real live data rather than trusting the code's apparent correctness.

Phase 7 — Multi-communicator: Tensor Parallel (P21 → P21.8)
This is where the project's architecture was most seriously tested. Every part of the system up to this point assumed exactly one communicator spans the whole job. A real 2-way Tensor Parallel job (combined with standard data-parallel training) broke that assumption in three separate, precisely-located ways: the aggregator never read the communicator ID at all; a rank number was found to be communicator-local, not a stable physical identity (the same physical GPU reported different rank numbers on records from its two different communicators); and message-size calibration was hardcoded against one specific workload's byte values. Critically, none of the actual statistical detection logic was found broken — it simply never received any data, because ingestion silently dropped 100% of it. This confirmed the fix was tractable plumbing, not a fundamental redesign.

The fix (P21.5) was built to a strict standard: fully dynamic discovery, zero hardcoded counts anywhere. It was validated far harder than planned — real data showed 6 distinct communicators on one node where only 2 were anticipated, directly proving the dynamic-discovery decision over any fixed-shape alternative. This same session found a real, previously-undiscovered bug in CV's own math: the variance formula is mathematically degenerate for any exactly-2-member communicator (a fault-showing rank always ends up with exactly one remaining peer, making standard deviation undefined). This meant every TP pair, at TP_SIZE=2, could never self-detect a fault directly — a real, structural limitation, not a bug to patch away.

Worse, when a fault occurred inside such a pair, the alert that fired named the wrong, healthy node — a cross-communicator cascade effect (the delay showed up in a different, larger, un-faulted communicator that happened to span the healthy machine). A confidently wrong answer is worse than an honest non-detection, and P21.6 fixed this by making any alert sourced from a communicator with a dependent, self-detection-incapable communicator explicitly disclose location uncertainty rather than presenting its guess as fact. A follow-up attempt at real cross-communicator localization found a second, distinct confound (a "position bias" — not the true global rank-0, but a structurally-privileged position within the smaller communicator, consistently outcompeting the real fault in a naive ranking approach) and was correctly withdrawn rather than shipped as a fragile, sometimes-wrong "fix."

P21.7 closed the deeper root cause behind several of these findings: Inspector's dump schema had no way to identify which physical GPU slot (0-7) produced a given record. A real schema addition (gpu_slot_index, captured via cudaGetDevice() on the correct thread — a real, subtle gotcha, since NCCL Inspector's dump thread is different from the training thread) fixed DCGM cause-targeting completely, and partially fixed rank-0 exclusion — but a second position-bias instance was found immediately, confirming this is a general phenomenon (different position, different underlying cause each time), not a single fixable artifact.

P21.8 finally tested a different, larger TP configuration (TP_SIZE=4) and found genuinely good news: at 3+ members per communicator, self-detection works cleanly, directly, with no cascade needed at all — the 2-member gap is specific to the smallest possible TP configuration, not a general multi-communicator problem. A different position-bias instance (the last TP-rank position, not the first) was found here too, on healthy data, correctly contained by the confidence-tiering safety net (never escalating past PROBABLE).

P21.6.1, much later, finally built the DCGM fallback originally scoped in P21.6: for any communicator below the self-detection floor, proactively query real GPU hardware telemetry (clock, thermal) for every member, rather than waiting for a peer-relative statistic that can never compute. This closed both the TP-training cascade case and, later, the TP-inference standalone case (see below) with real, live-validated evidence — and found two more real bugs along the way (a member-counting bug that silently broke the floor check, and yet another instance of the query-eval-time-vs-sample-time timestamp bug).

Phase 8 — FSDP (P22 → P22.5)
FSDP's real collective mix (ReduceScatter, AllGather) surfaced a genuinely new class of bug: the calibration window could permanently miss an entire collective type if it happened not to appear during the fixed initial sample window — a real, severe fault signal on ReduceScatter was completely invisible to the alert pipeline because that collective type had never been calibrated at all. Fixed generically: require a minimum occurrence count per collective type discovered, not just per communicator overall.

Fixing that surfaced a second bug: two different collective types sharing an identical byte size were being silently pooled into one statistical series once bucketing became more precise — traced to a query-layer blindness (the alert engine's bucket discovery didn't know about collective type at all, only the aggregator did). Fixed by threading collective-type awareness through every query, tracking dict, and persistence key.

A third, unrelated bug was found while validating this fix: IDLE_POWER_W, a hardcoded absolute power threshold calibrated against heavier workloads, misclassified a lighter-power workload's genuinely active GPU as idle. Fixed with a peer-relative power ratio instead of an absolute constant — the third instance of the exact same "hardcoded against one workload's profile" pattern in one project.

A real, severe aggregator scalability failure was also found here: under FSDP's higher real event rate, an unbounded accumulator (all_vals) grew without limit, eventually consuming 16GB of RAM and — critically — causing the aggregator to stop honoring its own --duration cutoff, which in turn caused a job-throughput check to misread the aggregator's own lag as the job slowing down, producing two false CONFIRMED/PAGE alerts against a perfectly healthy training run. Root-caused and fixed with a bounded rolling window, a deadline-aware polling loop, and a dump-timestamp-based (not wall-clock-based) throughput calculation — the last of which specifically removes the aggregator's own health as a variable in a check meant to measure the job's health.

Once fixed, FSDP's real detection floor was measured precisely: a moderate fault (a ~58-62% exec-time change) doesn't clear the natural variance ceiling of this large, cross-node communicator shape; a severe fault (~75-82% change, at the hardware's actual clock floor) does, cleanly and reliably. This is a real, quantified, disclosed characteristic — not a gap.

Phase 9 — MoE (P23)
The design phase (before any testing) correctly anticipated the core problem: MoE's AllToAll routing means peer comparison assumes comparable work per rank, which real, data-dependent expert routing violates by design. A real toy MoE layer (top-1 gating, 8 experts, all_to_all_single-based dispatch/combine) was built, requiring real engineering to combine with standard DDP (four separate DTensor/plain-Tensor integration issues, all fixed via legitimate mechanisms).

The single most important finding: Inspector had zero visibility into AllToAll traffic at all — not mislabeled, genuinely absent, because the plugin's event-activation mask never requested NCCL's point-to-point event flag. This was fixed (a real, contained schema patch, much like gpu_slot_index), and the resulting real event-rate multiplier was measured carefully and proactively (learning directly from the FSDP scalability lesson) before any training code was built on top of it.

MoE's real, data-dependent routing produced a second new class of scalability problem, distinct from FSDP's: not too much volume per bucket, but an unbounded number of buckets, since real per-token routing counts vary continuously. This was fixed with log-scale message-size coarsening — and doing so revealed that the original natural-variance ceiling measurement (~324.6) had been an artifact of severe under-sampling; the corrected, honest measurement was ~1,462.7 — nearly 5x higher.

The most consequential finding of the whole MoE arc: peer-relative statistics cannot localize a single-rank fault to a specific rank within AllToAll traffic, for a real, mechanistic reason — AllToAll is a synchronous collective, so when one rank is delayed, the waiting ranks show the elevated timing, not the delayed rank itself (which looks normal once it finally arrives and completes quickly). This was proven, not assumed, across three separate real injection attempts (two of which failed for their own interesting reasons: NCCL protocol-level channel symmetry rejection, and an RDMA verbs API limitation requiring a different, vendor-specific interface). The one that worked (a pure software delay) definitively confirmed the mechanism. Job-wide detection of the same fault does work correctly — MoE stragglers are caught, just not localized to a specific rank, a real and permanent architectural boundary distinct from — and worse than — the already-known 2-member self-detection gap.

Research into how other teams handle this (a 2026 industry paper on scalable straggler detection, "Guard," plus related work) confirmed this is a known, actively-researched problem industry-wide, and suggested a real, different-in-kind solution: periodic, isolated offline diagnostic sweeps between rank pairs, separate from live-job monitoring — a genuinely new capability, not a fix to the existing live-detection architecture, scoped as future work.

Phase 10 — DCGM causality expansion (P25)
The NVLink counter check was built to close a real, confirmed gap: TP's traffic runs exclusively over NVLink (TP pairs are always co-located on the same node), and the existing network check only ever reads InfiniBand counters — meaning a real NVLink fault on any TP job was completely undetectable, not just harder to catch. The check was built and reasoned correctly, with two honest limitations found: a genuinely non-monotonic DCGM field (caught before it could cause a wrong result) and a structural one (NVSwitch spreads traffic across all links so evenly that per-link participation may not reliably catch a partially-degraded single link — throughput and error-delta carry the real weight of detection here).

No real way was found to inject an NVLink fault on this hardware, despite trying three genuinely different approaches (diagnostic tooling, fabric management tooling, real engineered bandwidth contention). This is the first detector in the whole project that is correctly built and reasoned but has never been proven against a real fault — an honestly-labeled, different confidence tier from everything else.

The XID hardware fault code investigation found something equally important: this cluster's own chronic hardware fault (GPU 3) has never once logged a real XID event in this project's entire history. Every fault this whole project has ever validated has been a performance/counter signal — never a driver-logged hardware-fault event. XID's integration design was completed (reusing the exact pattern from the existing network check), but correctly marked PROVISIONAL rather than validated, since there is currently nothing real to validate it against.

Phase 11 — Workload breadth (P26)
ViT was built and validated cleanly — the fourth-through-sixth distinct workload shape overall, and specifically the one with the highest power profile tested (365-402W), confirming the three previously-fixed generic mechanisms work correctly on both sides of the spectrum, not just the low-power side that originally exposed them.

ResNet regression re-confirmation — a routine re-check of an already-validated workload — found two real, serious regressions that had crept in silently as shared infrastructure evolved: a workload-signature collision (ResNet's cross-job calibration reference accidentally matched nanoGPT's, comparing ResNet's genuinely different real throughput against the wrong baseline and producing a false page on a healthy run), and — far more seriously — a real, severe injected fault (z=512.9, one of the largest ever observed in this project) that never reached CONFIRMED at all, because coverage_guard's hardcoded rate floor (calibrated only against nanoGPT) treated ResNet's genuinely different, lower real throughput as permanently degraded, capping confidence regardless of signal strength. Both were fixed generically (reusing the same cross-job-reference infrastructure already built, rather than inventing new hardcoded numbers), and while validating the fix, a third instance of the same pattern (IDLE_POWER_W, see FSDP above) was found and fixed in the same session — discovered only because validation was pushed all the way through to the real end goal instead of stopping once the two originally-scoped fixes looked correct in isolation.

Inference produced the most structurally interesting result in P26. Pure data-parallel inference was confirmed, empirically, to produce zero cross-rank traffic — nothing to monitor, by design, now proven rather than just reasoned. Tensor-parallel inference at exactly 2 members needed (and got) the same DCGM fallback built for TP training. But TP-inference at 3+ members — a configuration size that works correctly for every other workload tested — produced a real, severe, sustained fault with zero detectable signal at any confidence tier, confirmed at the raw-field level (the fault genuinely never showed up in measured collective timing, not a threshold miss), while a milder, pre-existing anomaly in the same job was caught cleanly. This is currently the single most serious open, unexplained finding in the project — investigation into the mechanism (a leading, unconfirmed hypothesis: inference's forward-only collectives, or its much faster cadence, may not manifest the barrier-wait signature the whole detection system is built on) is in progress.

Phase 12 — Production infrastructure track (parallel to all of the above)
Throughout this whole arc, a separate, largely independent track has been ongoing:

Datasource routing — the original ask (get the aggregator's data somewhere the shared, company-wide Grafana could see it) went through several false starts: an OTel/vmagent path was proposed, investigated, and found not to exist as described; a direct-push path was confirmed reachable but blocked on the shared instance's 30-second dedup interval (destroying most of this pipeline's data). Eventually a live A/B test (run by a colleague) confirmed the shared vmagent does accept a real OTLP push after all — resolving a months-long open contradiction — but the dedup incompatibility remained the real, load-bearing blocker throughout.

The final decision: a dedicated, self-owned VMSingle instance (0s dedup) as the real detection backend, with only the low-resolution network-panel data ever retransmitted to any shared/central Grafana. This was chosen specifically because it's the only option that doesn't compromise the resolution the fault detection itself depends on.

The shared Grafana itself is being phased out in favor of a future centralized solution with no confirmed timeline or ingestion mechanism yet — a real, external dependency outside this project's control.

A real Helm chart (P26.5) was built for the VMSingle instance, as a genuine MVP for team review — matching the platform's own existing deployment convention exactly, with every configuration value grounded in real measured data from the reference instance's 9+ days of actual running history. One important, honestly-flagged limitation: the session that built it had zero Kubernetes RBAC, so the chart's core "survives a restart, self-heals" claim was validated only at the storage layer (data survives a process restart) — the live-cluster mechanism (Kubernetes actually noticing and recreating a dead pod) has never been exercised, and needs someone with real cluster access to confirm.

Phase 13 — Migration to a 6-node cluster, and the standalone VictoriaMetrics pivot
The project moved from the original 2-node cluster to a 6-node "soperator" H200 cluster. Most of the NCCL Inspector/bpftrace/gpu_slot_index layer transferred cleanly with per-node re-verification (see `migration_readiness.md` for the full, tedious, worthwhile detail — a stale pre-baked Inspector `.so` on every node, an IPv6-routing apt failure on one node but not others, three genuinely different bpftrace-wrapper states across three nodes checked). The one piece that did not transfer was VictoriaMetrics itself: the dedicated VMSingle Helm chart's Kubernetes RBAC block, already disclosed as unresolved on the original cluster, was re-checked and re-confirmed identically blocked here — a real `SelfSubjectRulesReview` came back with zero permissions again. Two clusters confirming the same block in a row is a pattern, not bad luck, and the project stopped waiting on it.

The fix: run VictoriaMetrics as a plain binary, launched via `srun` exactly like a training job, needing no Kubernetes access of any kind. This is not a workaround or a downgrade — `-dedup.minScrapeInterval=0s` and `-retentionPeriod=100y` give this standalone instance real properties the shared/VMSingle path never had guaranteed anyway (this project's own dedup investigation in Phase 12 is the same underlying problem this flag directly defeats). Every real test in every phase below ran against this standalone instance, launched on its own dedicated node so it never competed with training jobs for scheduling or CPU.

Phase 14 — The regression sweep, and the clock-lock discovery
With the full pipeline finally live end-to-end on real hardware for the first time (Inspector → standalone VictoriaMetrics → alert_engine, no shared-instance dedup problem, no RBAC block), the project ran its first full regression sweep: every previously-validated workload, re-tested together, on the same cluster, with a mandatory rank-cross-verification standard (record the real injected rank before checking alerts, then explicitly compare it against the flagged rank — "the alert fired correctly" without that explicit comparison was no longer accepted as sufficient evidence).

The sweep immediately surfaced a real, load-bearing problem with the project's own methodology: `nvidia-smi -lgc` clock-lock, the injection method three separate workloads (ResNet, ViT, TP-inference) had relied on because they lack a native software fault-injection mechanism, was found to produce zero measurable effect on this cluster's actual H200 hardware. This reframed a long-standing open mystery from Phase 11 — TP-inference at 3+ members showing a real, severe fault with zero detectable signal at any tier — as never having been a detection-engine gap at all. The fault had simply never been real; the injection method silently didn't work, and nothing before this session had checked the raw data closely enough to notice. The fix was to give each of the three affected workloads (plus FSDP, whose own STRAGGLER_SLEEP_MS convention turned out to be an unimplemented, comment-only placeholder rather than the real mechanism it was assumed to be) a real, validated `time.sleep()`-based software injection, gated by `STRAGGLER_SLEEP_MS`/`STRAGGLER_TARGET_RANKS` — the same convention nanoGPT-TP's own training script already used, now genuinely implemented everywhere. Built and validated one at a time: TP-inference showed a 198.6ms observed delta against a 200ms injection, a near-exact match confirming the mechanism itself was sound.

A second, separate open question from Phase 7 — whether physical ring adjacency on the NCCL communication topology explained certain cross-rank misattribution patterns — was closed this same phase with direct physical evidence: `nvidia-smi topo -m` showed a full NVSwitch mesh (NV18 links between every GPU pair), meaning there is no ring topology on this hardware to be adjacent within. Ten real trials found zero misattribution, confirming the hypothesized ring-neighbor DCGM fallback was never needed and should not be built.

With clock-lock replaced and ring-adjacency closed, the sweep's real results were mixed in an informative way: nanoGPT-DDP, ResNet, TP at TP_SIZE=4, and one of two ViT trials produced clean, exact rank matches. But TP at TP_SIZE=2, FSDP, a second ViT trial, and TP-inference all produced non-detections — no alert at all, not a wrong one. Investigating why, rather than accepting "sometimes it just doesn't fire," is what the next three phases are about.

Phase 15 — Closing the 2-member gap for software faults (Part 1)
The TP_SIZE=2 and TP-inference non-detections shared a real, reproducible raw-data signature: the injected target's own recorded collective-exec-time read LOW (it sleeps before entering the collective, so its own measured time in the collective is short), while its healthy partner's read HIGH (the partner is the one actually waiting). This is the exact inverse of what a naive "the elevated one is the straggler" rule would conclude, and it's a genuinely different failure mode from the DCGM-based 2-member fallback already built in Phase 7 (P21.6.1) — that fallback correctly, honestly returns no answer for a pure software-sleep fault, because there is no DCGM signature to find; it was built for hardware clock/thermal suppression, a different evidence type entirely.

Building the fix took several real iterations, each one caught by testing against live data before trusting it: a first design comparing each member's current exec-time against its own same-run historical average false-fired on ordinary warmup dynamics, since early iterations are naturally slower before caches and NCCL channels settle. Redesigning to compare each member against the cross-communicator peer median (every other same-shape TP-pair's members on the same job) found and fixed a second real bug — the comparison direction was backwards in an intermediate build. The corrected version then false-fired specifically and reproducibly on rank 0's own TP pair, with near-identical numbers (the same ~1.8x split) across independent runs — the project's own long-documented rank-0 background-overhead bias, not a new phenomenon, closed by reusing the existing real-identity rank-0 lookup already built for a different purpose in Phase 7.

The final design — cross-communicator peer-median comparison, rank-0 excluded by real identity, persisted through the same 3-consecutive-sample discipline used everywhere else in this project — was validated cleanly on both original failing cases: TP_SIZE=2 (target rank 3) and TP-inference (target rank 2) each produced exactly one CONFIRMED alert on the exact injected rank, zero false positives, confirmed by explicit gpu_slot_index cross-reference rather than trusted at face value.

Phase 16 — FSDP's real bug wasn't dilution (Part 2)
The FSDP non-detection was assumed, going in, to be a dilution problem — FSDP's fine-grained per-block collective structure spreading a real signal across too many small, independent statistics. Direct investigation of the raw data disproved this immediately: FSDP uses exactly one communicator, not many, and the effect size on the correct rank was large, not diluted — stronger, in fact, than the effect size on the rank that got incorrectly flagged instead. The real bug was a poll-timing race: `_check_mean`, unlike its sibling `_check_cv`, had no persistence or lookback at all — a bare instant query that only ever sees whichever value VictoriaMetrics considers current at the exact instant of the poll. node_aggregator's own internal computation had correctly identified the true fault (a stronger z-score than the wrong rank's own), but the specific window in which that computation was visible fell between two polls and was gone by the next one.

Fixing this surfaced two further real bugs, neither of which had anything to do with FSDP specifically, both found only by testing the fix against live data rather than trusting it once it looked plausible. First: VictoriaMetrics's own comm/bucket discovery queries don't reliably restrict to genuinely recent activity — one poll cycle was checking 136 distinct communicators, many from workloads that had finished hours earlier the same session, silently inflating real poll wall-clock time far past the intended interval and starving the current job's own buckets of timely checks. This is not an FSDP bug; it had likely been quietly degrading detection timing for every workload tested this entire project, unnoticed because the resulting delay usually still fell inside whatever window a given test happened to use. Second, once the query was correctly widened to bridge the resulting gap: `timestamp()` does not compose with `max_over_time()` in this VictoriaMetrics instance's PromQL engine, silently discarding every result through logic that was correct for a different query shape. Both were real, previously-undiscovered infrastructure bugs, uncovered only because Part 1's small-comm work had already established the discipline of verifying a fix's raw underlying data rather than trusting its headline alert count.

Once both were fixed, the real remaining question was pure timing margin, not correctness: FSDP's own smaller administrative collective needs close to a full 130-second test's entire duration just to accumulate its first real statistics window. Given a genuinely adequate window (300 seconds), the fix correctly flagged the exact injected rank, and the healthy baseline stayed clean.

Phase 17 — MoE's cross-job baseline, closed in two passes (Part 3)
The MoE non-detection from Phase 14 (a real, confirmed 8.4x AllToAll slowdown under a job-wide network fault, with zero alert of any kind) traced to the job-wide `uniform_slowdown` detector's own cross-job-reference mechanism never having enough historical data to establish a baseline — not "not enough runs yet" in the ordinary sense, but a real, structural unreachability. The gate that must pass before a workload signature is even computed requires a live bucket-count denominator to hold byte-exact identical across three consecutive checks; MoE's real, data-dependent expert routing keeps discovering new, rare message sizes indefinitely, so that denominator never truly stops growing, confirmed directly via a dedicated 700-second seeding run — 5.4x the original test's length — that still never once reached the gate.

The fix relaxed exact equality to a small relative tolerance, reusing this project's own existing "how large a deviation is significant" threshold rather than inventing a new one, and was validated with real, decisive evidence: a fresh healthy run established a genuine throughput reference in under 200 seconds, where the mechanism had never once succeeded before, at any duration.

That same validation immediately surfaced a second, independent bug the first fix's own success made visible for the first time: a real MoE netfault run's own workload signature differed from three real, matching healthy reference signatures by exactly one rare message size that simply hadn't occurred yet by the netfault run's own (now finally reachable) stabilization point, since its slower real pace meant less real training had happened by then. A one-entry difference in an exact-string match is still a complete mismatch, and the run fell back to self-calibration — a separately pre-existing, already-documented limitation (self-calibration is mathematically blind to a fault present since a job's own launch) — meaning the real, confirmed fault still produced no alert, for a genuinely different reason than before.

This second fix — comparing message-size sets by Jaccard distance instead of exact string equality, with the coarser communicator-count-and-collective-type signature still matched exactly so genuinely different workloads can never blur together — was implemented and reasoned carefully, including an explicit regression check confirming DDP, TP, FSDP, and MoE's own structural signatures remain pairwise distinct by construction. It could not be live-validated before the cluster this work was running on became occupied by unrelated external jobs for an unpredictable, multi-day duration (see Phase 18) — the decisive re-test (confirming the netfault run's signature now matches its healthy references and the job-wide detector correctly fires) is the first thing scheduled on whatever cluster this work resumes on next.

A separate, real, and still entirely unexplained finding surfaced during this phase's own validation runs: a host-load alert fired identically, three times in three independent healthy MoE test runs, on one specific physical node, with no corresponding job visible to explain the real (if small) CPU load difference it measured. Not caused by anything touched this session — worth watching for on the next cluster, to learn whether it was a property of this pipeline's own detection logic or a property of that one physical machine.

Phase 18 — A second migration, mid-stream
Partway through validating Part 3's fix, the two nodes this entire regression sweep and gap-closure arc had used became occupied by a sequence of unrelated external jobs with independent multi-day Slurm time limits — a real, unpredictable block with no visibility into an actual completion time, not the kind of transient scheduling contention this project had routinely worked around elsewhere. Rather than wait an indeterminate number of days, the decision was made to migrate the whole project to a fresh, dedicated 2-node H200 cluster — the same discipline Phase 13's migration already established: bring everything, verify nothing by assumption, and treat every "confirmed on the previous cluster" claim as exactly that, not as automatically true on the next one. This document, `codebase_reference.md`, and `migration_readiness.md` were updated together specifically so that migration could happen without silently losing any of the real findings above.

The throughline
If there's one lesson that recurs across every single phase of this project, it's this: the same class of bug — a value calibrated against one specific, familiar case, silently wrong the moment something genuinely different shows up — has been found and fixed at least five separate times, in five different parts of the system (a query timestamp extraction, three unrelated hardcoded thresholds, a cross-job reference scheme). Each time, it was caught not by code review, but by deliberately stress-testing the system against something new and checking the real end-to-end result rather than trusting that a fix compiled correctly in isolation. That discipline — build it, break it on purpose, check the raw data, don't stop at the first plausible-looking result — is the actual reason this project's findings are trustworthy, and it's the standard every future extension of this work should be held to.

The pattern recurred at least three more times in the P27-era phases above — clock-lock assumed to work on any H200 until it was checked directly and found not to; exact-string signature matching assumed sufficient until a real, slower run's own natural variability broke it; and a fix's own success (Part 3's first pass) immediately surfacing a second, previously-invisible bug the first one had been quietly masking. Nothing about this project reaching its most mature state yet has made this discipline less necessary — if anything, each new phase keeps confirming it's the only thing that's actually caught these bugs, every time.
