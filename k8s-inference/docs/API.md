# API

*For developers who call the platform: the customer API, its modes and its shape.*

The served contract is `/openapi.json`, generated by FastAPI from the shared request and response
types in `services/api/schemas.py` and the routes. `make openapi > openapi.json` exports the same contract
locally; there is no separately maintained specification. Contract tests validate actual responses
against those types and reject undeclared fields. Summary:

```
GET    /v1/models[/{model}]          the built-in classes (catalog/models) and the models defined through the API, with live endpoint status
POST   /v1/models                    define a model (admin key, fleet API only): a container plus a few knobs -> stored, rendered, registered
PUT    /v1/models/{model}            replace a definition (new version); DELETE /v1/models/{model} removes it (built-in classes: 409)
GET    /v1/models/{model}/history    every version of a definition: who changed what, when (admin key)
POST   /v1/models/{model}:invoke     body {mode, input, region, priority, timeout_s} -> operation (sync returns the result inline)
GET    /v1/operations[/{id}]         status, attempts, timings, region, gpu_class (per-class images), cost
GET    /v1/operations/{id}/result    result (async) or presigned artifact links (run)
POST   /v1/operations/{id}:cancel
POST   /v1/operations/{id}:resume    FAILED/CANCELLED run -> new operation on the same checkpoint volume, same region
POST   /v1/artifacts/uploads         presigned upload URL scoped to the tenant prefix
GET    /v1/artifacts/{uri}           presigned download of a tenant object (an operation's: authorized like its result)
GET    /v1/endpoints[/{id}]          the endpoints of the catalog models per region (`region=`); PATCH scaling (admin key)
GET/POST /v1/keys, PATCH/DELETE /v1/keys/{alias}, GET /v1/keys/me   API keys of the tenant (fleet API; admin key for writes; PATCH changes budget, allowed models, expiry)
Idempotency-Key header on every mutating call
```

One entry point: `https://api.<control cluster host>` (the fleet's API on the control cluster: models, runs,
operations, keys, sync and async calls for every region; `docs/ARCHITECTURE.md` "One API"). Streaming and
WebSocket calls go to the endpoint's own gateway hostname (`https://<model>-predictor.models.<region host>`,
the same key; `docs/EDGE.md`). A host is `<gateway ip>.sslip.io` or `<cluster>.<domain>`;
`./stack.sh output platform control` prints the URLs of a fleet. A run is placed in the cheapest free region
among the model's deployments by its GPU preference (`docs/JOBS.md` "Fleet placement"); `region` pins it; a
sync or async call for an endpoint in another region than the control cluster's is served through that
region's gateway. Keys are the same everywhere (one fleet database).

Modes: `sync`, `async`, `run`, declared per model; `async` may be requested per call. `async` and
`run` operations are Kubernetes Jobs in the tenant namespace of the region (`docs/JOBS.md`): a run
keeps its checkpoints on a per-operation volume, resumes on its own after a spot interruption and
by `:resume` after a failure or cancel. Endpoints are created, changed and deleted through the model
API ("Models" below), on the fleet API only. Admission limits are not in the API: Kueue bounds concurrent
runs (the fleet's profile queues), the key's budget bounds every call ("Keys" below; LiteLLM's own `rpm_limit` and
`max_budget` on its OpenAI route), and an
Envoy Gateway global rate limit caps each key (distinct `Authorization` header, counted in Redis
across replicas): 600 requests per minute on the API route, 3000 per minute on the predictor hosts. Two bounds
are the API's own: a call's `timeout_s` is 1 s to 14 days (a run has a deadline, no longer: the long-run contract, a 14-day MD run with a GPU-second budget needs its explicit timeout; a sync call waits, bounded by the API's own proxy timeout), and
the `input` of a run or an async call is at most 60 KB (413 above it: pass large inputs by reference, an artifact
upload or a binding).

## Models

A model is defined through the API, never in `terraform.tfvars`. `POST /v1/models` (admin key) takes the
shape of a model definition: a container plus a few knobs.

```json
{"id": "my-llm", "kind": "endpoint",
 "image": "vllm/vllm-openai:v0.11.0", "args": ["--model", "<org>/<model>", "--port", "8000"],
 "env": {"HF_HOME": "/weights"}, "port": 8000, "protocol": "openai", "served_model": "<org>/<model>",
 "gpu": {"count": 1, "classes": ["h100", "l40s"]}, "scaling": {"min": 0, "max": 2, "container_concurrency": 4},
 "regions": ["eu-north1"], "weights": {"path": "my-llm", "mount_path": "/weights"}}
```

`protocol` is `openai | http | websocket | grpc`; `gpu.classes` lists the classes the image runs on,
preferred first; `regions` defaults to every region with a pool of one of the classes; `kind: job`
defines a run class instead (`cpu`, `memory`, `cpu_limit`, `memory_limit`, `ephemeral_storage`, `ephemeral_storage_limit`, `disk_gi`, `scratch`, `parameters`, `delegates`, `retry`; requests are what the scheduler guarantees, limits what a container may grow to; `delegates` names the run classes a graph rooted on this class may bind stages to, docs/JOBS.md "Delegated stages"). The full field list is
the module docstring of `services/api/models.py`; the response schema is `Model` in `services/api/schemas.py`.

### Scaling

`scaling` is one vocabulary (`ScalingSpec` in `services/api/schemas.py`), the same on a model definition, on
`GET /v1/endpoints` and on `PATCH /v1/endpoints/{id}`: `min` and `max` replicas per region;
`metric: concurrency_utilization` (the default) scales on `target` percent (1-100, default 100) of
`container_concurrency`, the hard per-replica request limit (1-1000, default 1); `metric: requests_per_second`
scales on `target` requests/s per replica (default 5) with no concurrency limit; `cooldown_s` delays scale-down,
`window_s` (6-300, default 30) is the metrics averaging window, `idle_s` keeps the last replica after the decision
to scale to zero. The API writes the complete
policy back, so a read never has to guess a default. Rendering onto Knative: `concurrency_utilization` is the
`concurrency` metric with `container_concurrency` as the scale target and `target` as its utilization percentage;
`requests_per_second` is the `rps` metric at 100 % with `containerConcurrency` 0.

What happens on a write: the definition goes into the fleet database (table `models`: id, kind, spec, the
rendered entry, version, `managed_by`, created/updated by and at) and every write into `models_history`;
the API renders the endpoint on every cluster of the model's regions (`services/api/render_endpoint.py`;
server-side apply through the api-agent identities of the regions) and registers an
OpenAI endpoint as a LiteLLM model group whose `api_base` is the endpoint's gateway hostname in that region.
`PUT` replaces the definition (version + 1), `DELETE` removes the endpoint everywhere and keeps the last
version in the history, `GET /v1/models/{model}/history` lists the versions (admin key).

**Model groups and the router key.** A LiteLLM model group calls the endpoint over its public gateway
hostname, and the edge on those hostnames accepts only a key of the fleet. The group therefore calls as
the fleet's router key: a row of the `keys` table with role `router` (tenant `platform`, alias `router`, no
budget, no expiry, every model), whose value the platform stage generates once per fleet (Terraform,
`stack/platform/router-key.tf`, Secret `api/router-key`) and the control API reads as `ROUTER_KEY` and
upserts at every start (`services/api/keys.py` `ensure_router`). The caller's own key is checked first:
LiteLLM applies its budget, rate limit and spend before it routes to the group, then the gateway's
authorize hook sees the router key, which it accepts without a budget check and never bills; the per-key
rate limit of the edge (`SecurityPolicy model-key-check`) counts those calls against the router key, not
the caller. Every other API route refuses the router key (403). Without the Secret the API deploys the
endpoint and registers no group (a warning in the write's response and in the log): the endpoint still
answers through `POST /v1/models/{model}:invoke` and its gateway hostname with any tenant key. The router
key is never returned by the API.

Accounting is split by entry point: a call that enters through LiteLLM (`/v1/chat/completions` on the
`litellm.` host) is accounted by LiteLLM on its own record of the key (tokens, `max_budget`, `rpm_limit`);
a call through `POST /v1/models/{model}:invoke` or the endpoint's gateway hostname is accounted by the
platform: the key's budget and spend in the fleet database, GPU runs charged by the billing CronJob
("Keys" below, docs/RELIABILITY.md "Accounting and budgets").

Writes land in the fleet database (the API answers `POST`, `PUT`, `DELETE` and `/history` with 409 without
`DATABASE_URL`). The built-in classes (`hello-run`, `container-run`, `distributed-run`) are files and answer
writes with 409 too. `images` (per GPU class, `docs/SCHEDULING.md`), `deployments.<region>.variants` and
`routing` ("Variants" below) are implemented.

The acceptance probe (`tools/verify.sh`) uses this path: with `acceptance.example_endpoint = true` (the
default) it creates `llm-example` with the first admin key, waits for it, calls it once and leaves it as
the first model of the fleet.

Run classes may declare `data: {"path": "refdb/uniref", "mount_path": "/data", "readonly": true}`: a directory of
the tenant's area on the region's shared filesystem mounted into every run of the class (docs/JOBS.md "Shared data").

### Loading large weights

vLLM's default loader reads one safetensors shard at a time, about 170 MB/s from the shared filesystem; its
Run:ai streamer loads the same files with many streams at about 5 GB/s (806 GB in 2.6 min on a B300 node). Put `--load-format runai_streamer --model-loader-extra-config '{"concurrency": 32}'` into the command
of any vLLM endpoint whose weights live on the filesystem, and `VLLM_CACHE_ROOT=/weights/vllm-cache` in its env so
the torch.compile cache survives a restart (the first start of a trillion-parameter model spends about 25 min there).

## Keys

A key is `sk-` + 40 characters, shown once at creation; the fleet database (`keys` table, `services/api/keys.py`)
holds its sha256, alias (unique per tenant, `<tenant>-<name>`), tenant, role (`user`, `admin`, `router`),
model allow-list (empty = every model), budget in USD (null = unlimited), spend, expiry and block flag. Every
API checks the key on every request (hash lookup, cached `AUTH_CACHE_S` = 30 s): blocked, expired and
budget-exhausted keys and the allow-list are enforced on the catalogue, `:invoke`, the operations and the
gateway's authorize hook of every endpoint hostname. The first keys of a fleet are the tenants' `keys` of
`terraform.tfvars` (the platform stage writes them with `python -m keys bootstrap`, `./stack.sh output platform
control -json tenant_keys` prints them); an admin key then mints user keys of its tenant through
`POST /v1/keys` (budget, models, `expires_days`), edits them (`PATCH`) and revokes them (`DELETE`), on the
fleet API. Every tenant key is mirrored into LiteLLM with the same value (best effort; the fleet database is
the source of truth) so it also works on LiteLLM's OpenAI route. `GET /v1/keys/me` shows the calling key.

**Scopes and limits beyond the USD budget.** A key may carry `scopes` (what it may do; empty = everything of its
role): `invoke:sync`, `invoke:async`, `run:submit`, `run:control` (cancel, resume, export), `read:catalog`,
`read:operations`, `read:results`, `read:logs`, `read:metrics`, `artifacts:write`. Every direct path checks its
scope (403 `key scope <x> required`), the gateway's authorize hook included. Three further limits, each in its own
unit and nullable (null = unbounded): `budget_requests` (remaining calls), `budget_gpu_seconds` (remaining GPU
seconds) and `max_concurrent` (operations in flight), plus `rate_limit` `{requests, window_s}`. They are enforced
at admission in one database transaction per key (`keys.admit`: the key row is locked, so two API replicas never
admit past a limit together): a call or run takes a slot and a request; a run on a key with a GPU-second budget
reserves its GPUs times its `timeout_s` (such a key must give `timeout_s` on a GPU run, 400 otherwise) and the
measured GPU seconds replace the reservation when the attempt is billed; a sync call holds its slot for the
call. One `:invoke` and the gateway authorization of its own proxied call count once; a call that reaches an
endpoint hostname directly counts once at the hook; a replay with the same `Idempotency-Key` counts once.
Exhausted budgets answer 402, a full concurrency slot or rate window 429. `GET /v1/keys/me` shows the limits,
what was spent against them, and for imported keys the legacy `principal_id` and metadata.

**Ownership and continuations.** Every operation records its owner (the key's principal, migration 9), so a key
never reads, cancels, resumes or exports another principal's operations even inside the same tenant namespace; an
idempotency key is scoped to its owner (the same request under the same key from another key of the same principal
is a replay of the existing operation, on its original billing key); a reservation is refunded when the Job's
creation fails after admission. A run is one logical operation for the key's limits (migration 11, the run ledger):
the root takes the slot and the request once; every continuation (resume, export retry, application finalizer,
fallback, automatic recovery) joins the root's reservation as a member after the run's current head (a continuation
of anything but the head is 409), on the root's original key, which is checked again (blocked 403, expired 401); a
computing member with a GPU-second budget reserves its GPUs x timeout (402 when it does not fit next to what is
reserved and unknown), a transfer-only member nothing. Billing settles each member with its measured GPU seconds; a
GPU attempt that ended without a trustworthy measurement (a lost worker) stays `unknown`: its bound keeps counting
against the budget until an operator settles it (`keys.settle_unknown`), it is never charged as zero. A run cancelled
before it started settles at zero. The slot closes when no member is active; a later manual continuation re-acquires
it (concurrency re-checked, no second request). `GET /v1/keys/me` reports `usage`: operations in flight, reserved and
unknown GPU seconds. A key with any finite limit is admitted on the synchronous and run paths: a shared endpoint
cannot measure a key's GPU time, so a finite GPU-second budget answers 501 at the endpoint hook; a direct endpoint
call cannot hold a concurrency slot (501 unless the call is the API's own admitted call: `x-serverless2-admitted`, the HMAC of the key, the model and the operation, next to `x-serverless2-operation` and `x-serverless2-attempt`; the hook verifies on every call that the operation holds a live reservation on the key and is not cancelled, and that the caller's Job is the key's and the model's and the attempt one of its live pods, which lets an `invoke:async`-only key's endpoint call probe readiness and post its one inference through the gateway and nothing else; a release or cancel closes it at once); bounded asynchronous calls
answer 501 until the durable async call exists. Unbounded keys and keys created through `POST /v1/keys` are not
affected.

**Importing keys.** `POST /v1/keys:import` (an admin key; the keys of its own tenant only) and
`python -m keys import <file.json>` (an operator with database access) take pre-hashed records
(`{"keys": [{"hash", "alias", "tenant", "principal_id", "models", "scopes", "budget_usd", "budget_requests",
"budget_gpu_seconds", "max_concurrent", "rate_limit", "expires", "blocked", "preview", "metadata",
"created_at"}], "dry_run": false}`): the sha256 of the exact bearer value, never the value, so an existing
client keeps its key without rotation. The import is idempotent and all-or-nothing: a new hash and alias is
inserted, the same key with every field equal is unchanged, anything else (the hash under another alias or
tenant, the alias with another hash, the same key with changed limits, grants or principal) is a conflict and
the whole batch is refused with 409 and the list; invalid records are 400 with per-record reasons; `dry_run`
reports the classification and writes nothing. Imported keys are user keys; a scope the platform does not know
imports the key blocked (reported under `blocked_for_unknown_scope`) rather than widening it; grants for
models not deployed yet are kept as written; the role, limits and grants of an existing key are changed through
`PATCH /v1/keys/<alias>`, never by an import. Imported keys have no LiteLLM mirror (there is no value to
mirror): they work on the API and the endpoint hostnames, not on LiteLLM's own route (`not_mirrored` in the
report).

## Waiting runs

A QUEUED run reports `phase` and a bounded `reason` so a cold start is not an unexplained queue: `waiting_for_admission`
(no cluster admitted the Workload yet; `reason` is Kueue's condition message: quota, nomination), `waiting_for_node`
(admitted on `cluster`; the pod has no node: the scheduler's message, typically a pool scaling from zero or a full
pool, or no pod yet) and `starting` (scheduled; a container is waiting: the init containers, an image pull). `cluster`
names the admitting worker's **configured cluster id** (the tfvars id placement, identities and `allowed_clusters` are
keyed by; `region` is the Nebius region, two ids may share one) from admission on, before any attempt record exists;
attempt records and the uploader's acknowledgement carry the same `cluster` and `region`; `attempt_id` stays the
newest authenticated attempt (null until the uploader's first record), the pending pod is listed in `attempts`. Read
from the pod the API already lists, never from Events; `phase` is null outside QUEUED.

## Chains

A resume, a capacity fallback or an automatic recovery continues an operation as a new member of a chain
(`root_operation_id`, `resumed_from`, `recovered_from`). Any member, and any handle that resolves to one, reports the
chain's history next to its own state: `id`, `status`, `attempt_id`, `epoch`, `cluster`, `checkpoint_*` and `revision`
are the effective member's; `created_at` is the root's submission time; `started_at` the chain's first attempt;
`attempts` every attempt of every member in order, each with `operation`, `attempt_role`, `gpu_class`, `image`,
`image_digest`, times and `gpu_seconds` (measured main-container time x GPUs; `null` without an end record: nothing
is guessed); `chain` one entry per member (`id`, `created_at`, `status`, `gpu_class`, `cluster`, `reason`,
`gpu_seconds`, `gpu_seconds_complete`, `cost`); `gpu_seconds` and `cost` the measured totals over the chain
(`gpu_seconds_complete: false` while an attempt has no end record); `successor_created_at` when the newest successor
was created (its own first attempt may wait for capacity). An operation outside a chain carries none of these fields.

## Stages

A root that declared `execution.graph` carries `graph` on its handle (`status`, `stages[]` with `id`,
`depends_on`, `operation`, `status`, `attempt_id`, `result_ref`, `reason`, `deadline_at`, `cancelled`) and is
terminal only with its stages; a stage carries `stage` (`root`, `id`, `depends_on`, `reason`) and waits with
`phase: waiting_for_dependencies`. The rules (sealed graph, one operation per stage, same owner and key, the gate,
failure, cancel, deadline) are in docs/JOBS.md "Stage composition".

## Weights of an endpoint

`weights: {path, mount_path, env, read_only, prepare}` on an API-managed model (`POST /v1/models`): the region's
shared weights filesystem under `path` (the model id by default) at `mount_path` (`/weights`). `read_only: true` mounts
a verified, immutable payload readOnly and skips the prepare step that would create and open the directory;
`prepare` overrides that step explicitly. Defaults: writable, prepared.

## Variants

One endpoint may run as several deployments in a region behind its one name, in priority order: a warm floor on
reserved GPUs and scale-to-zero overflow on spot, a cheaper class for budget requests. In the model definition:

```json
{"id": "chat", "kind": "endpoint", "protocol": "openai", "image": "vllm/vllm-openai:v0.31.0",
 "images": {"l40s": "vllm/vllm-openai:v0.31.0-l40s"},
 "gpu": {"count": 1, "classes": ["h100", "l40s"]},
 "deployments": {"eu-north1": {"variants": [
     {"name": "reserved", "pool": "h100-reserved-1x", "min": 1, "max": 2},
     {"name": "spot",     "pool": "h100-spot-1x",     "min": 0, "max": 4},
     {"name": "cheap",    "pool": "l40s-spot-1x",     "min": 0, "max": 2}]}},
 "routing": {"field": "tier", "map": {"fast": "reserved", "budget": "cheap"}, "default": "priority"}}
```

Each variant is its own Knative service: the first keeps the model's name (`chat`), the others are
`<id>-<variant>` (`chat-spot`, `chat-cheap`), each with its pool, replica bounds and image (`variant.image`, else
`images.<class of the pool>`, else the model's image). All of them carry the model's labels, hostname certificate
and authorizer. A request through `:invoke` goes to the variant that `routing.field` selects (`map` maps the field's
value, dotted paths allowed), else to the `default` variant, else (`priority`) to the first variant with a ready
replica, else to the first one. Through LiteLLM the model group lists every variant of every cluster as a deployment
with its priority (`order`), so the OpenAI route tries the warm floor before the overflow. `GET /v1/endpoints` reports
`variants` (name, object id, pool, bounds, image, live state) and `routing`. `images` alone (no variants) gives a
plain deployment the image of its pool's GPU class. Regions named under `deployments` define where the endpoint
runs; a region without variants keeps the automatic pool choice. A redefinition that drops a variant (or a region)
removes its service, its LiteLLM deployment and, once Knative has torn its routes down, its authorizer; a dropped
warm variant holds no GPUs beyond that.

## Sessions (live streams to an endpoint)

Off unless the fleet enables it (terraform.tfvars `sessions.enabled`; `GET /v1/sessions` is 404 while off). A session is
an admitted stream for workers that hold GPU state across one long connection (speech): one claim, one connection, one
worker pod, released once; `services/api/sessions.py`.

| Step | Who | What |
|---|---|---|
| `POST /v1/models/<id>:session` `{timeout_s, region}` | the caller (`invoke:sync`) | admission on the key as a run's root: one concurrency slot, one request, and for a key with a GPU-second budget the endpoint's GPUs x `timeout_s` as the bound. Answers 202 with a one-time `claim_token`, `expires_at` (the claim must be presented within `sessions.claim_ttl_s`, 120 s by default) and `deadline_at` (`timeout_s` after creation) |
| the connection | the caller | presents the claim once: `Sec-WebSocket-Protocol: s2-session.<token>` on an upgrade, or the header `x-serverless2-session-claim: <token>` on a plain HTTP request (NDJSON streaming). The gateway's authorization hook binds it with a compare-and-swap (`claimed -> bound`, a server-generated connection id): exactly one connection ever binds a session, across API replicas; a second presentation, an expired, cancelled or foreign claim is 401. The hook injects `x-serverless2-session` and `x-serverless2-connection` towards the worker and refuses (403) any client that supplies those headers itself; the claim token is never logged |
| `POST /internal/sessions/<id>:attach` `{connection, worker_session_id}` | the worker pod, with its own ServiceAccount token | before any decoder, reset, feed or GPU work: `bound -> attached` for the injected connection id only. The pod is verified server-side (TokenReview on the session's cluster with `sessions.token_audience` or the cluster's, the pod's namespace/name/UID from the token's claims, the pod object with the same UID, the endpoint it belongs to = the session's model); nothing is taken from headers. Idempotent for the same connection and pod UID; 409 for another connection, a second worker, or after the attach wait, a cancel or the deadline (fenced for good) |
| `GET /internal/sessions/<id>` | the attached worker only | `status`, `cancel_requested`, `cancel_reason`, `deadline_at`: the worker polls it (or reads its own socket) to learn of a cancellation |
| `POST /internal/sessions/<id>:release` `{connection, outcome, gpu_seconds}` | the attached worker, after its own post-done cleanup | `attached -> ended`; the key's slot goes; `gpu_seconds` measured becomes spend, `null` (no metering) leaves the session `unknown` and its bound against the budget, never a measured zero. Idempotent for the same pod. Outcomes: `done`, `cancelled`, `disconnected`, `busy`, `error` |
| `POST /v1/sessions/<id>:cancel`, the deadline, a client disconnect | the owner, the reconciler, the transport | cancellation *requests*: nothing is released by them. A session nobody bound ends at once (zero: no worker was reached). A bound or attached one keeps its slot until its worker releases it or its pod (exact UID) is gone or finished, which the reconciler confirms every 15 s (`worker_lost`, usage unknown). Never a replica-wide drain |
| `GET /v1/sessions`, `GET /v1/sessions/<id>` | the owner (`read:operations`) | `status` (`claimed`, `bound`, `attached`, `ended`), `outcome`, `cancel_requested`, `attached`, `worker_session_id`, the timestamps, `gpu_seconds`, `usage` (`measured`, `unknown`, `none`) |

No reconnect: a dropped connection ends at the worker (`disconnected`), the token binds once, a new session is a new
admission. A bound session no worker attached within `sessions.attach_wait_s` (60 s) ends `unattached` with usage unknown.
Settlement on the key's ledger happens exactly once per session (the reconciler retries what a crash left unsettled).

## Bindings and execution options (runs, and endpoint calls with private I/O)

`PUT /v1/bindings/{ref}` `{"data": {"<key>": "<value>", ...}}` (at most 64 KiB) stores a confidential input of the
tenant; `GET /v1/bindings` lists them (reference, bound operation, keys; never the data); `DELETE /v1/bindings/{ref}`
revokes one (both need `artifacts:write`). An endpoint call (`mode: async`) may name a binding too: its request and
its output destination then come from the binding (docs/JOBS.md "Endpoint calls with private input and
application-owned output"). A run names a binding as `execution.private_input_ref`; the other fields of the `execution` block
(`io_mode`, `profile_ref`, `workload_identity_ref`, `placement`, `recovery`) are described in docs/JOBS.md
"Execution options". `GET /v1/fleet` carries `execution` (capability discovery: io modes, the tenant's identities and
profiles, the regions' OIDC issuers, the `recovery` policies and bounds the fleet supports, the application `finalize`
roles and retry bound, docs/JOBS.md "Finalization by the application"). `POST /v1/operations/{id}:resume` takes an optional body
`{"checkpoint_ref": "...", "gpu_class": "..."}`. Operations report their resolved block as `execution` and their lifecycle
(`root_operation_id`, `attempt_id`, `epoch`, `revision`, `cluster`, `image_digest`, `export_state`, `result_ref`,
`checkpoint_ref`; docs/JOBS.md "Attempts and finalization"); `GET /v1/operations/{id}?since=<revision>` answers 304
while nothing changed; `POST /v1/operations/{id}:export` retries a failed export without rerunning the simulation;
`POST /v1/operations/{id}:resume` with an `Idempotency-Key` header replays one continuation; a handle that capacity
fallback superseded resolves to its successor (`requested_id` names the handle used).

## Multi-node endpoints

An endpoint definition with `nodes` > 1 serves one model from that many whole nodes at once (tensor-parallel inside
a node, pipeline- or expert-parallel across them): the platform renders a LeaderWorkerSet (Kubernetes SIG) instead
of a KServe InferenceService. `gpu.count` is the GPUs per node and must be a whole-node preset of the class
(`8` on H100/H200/B200/B300); `command` runs on the leader, which serves `port`, `worker_command` on the other
nodes; every pod gets `NNODES`, `GPUS_PER_NODE`, `WORLD_SIZE`, `NODE_RANK`, `MASTER_ADDR` (the leader's hostname),
`MASTER_PORT` and `NCCL_SOCKET_IFNAME` next to the LeaderWorkerSet's own `LWS_LEADER_ADDRESS`, `LWS_GROUP_SIZE`
and `LWS_WORKER_INDEX`, so vLLM's multi-node recipe works unchanged:

```json

 "scaling": {"min": 0, "idle_s": 1800}, "regions": ["us-central1"]}
```

The example above is vLLM's Ray-based pipeline-parallel recipe; the stock `vllm/vllm-openai` image ships no Ray,
so without a custom image use vLLM's Ray-free data-parallel mode instead (one full copy of the model per node,
tensor-parallel inside the node; the leader serves, the workers run `--headless`): leader
`vllm serve ... --tensor-parallel-size 8 --data-parallel-size 2 --data-parallel-size-local 1 --data-parallel-address $(hostname -i) --data-parallel-rpc-port 13345 --port 8000`,
workers `... --data-parallel-address $LWS_LEADER_ADDRESS --data-parallel-start-rank $LWS_WORKER_INDEX --headless`
(verified with Kimi K3 on two B300 nodes). Over Ethernet the pods get `NCCL_IB_DISABLE=1`: the nodes
carry Mellanox NICs the pod does not hold, and NCCL's InfiniBand transport fails with "unhandled system error" otherwise.

Placement: the pool whose preset has exactly `gpu.count` GPUs per node, reserved before on-demand before spot;
`interconnect` `none` (default) prefers plain pools and runs NCCL over Ethernet, which is right for pipeline
parallelism and lets the pool scale from zero; `preferred` takes an InfiniBand pool when the region has one,
`required` only those, and the pods then claim every fabric NIC through DRA. The cluster autoscaler never adds
InfiniBand nodes; the dispatcher raises the pool's floor to the endpoint's node count while it is started and
restores `min_nodes` after it is stopped (docs/SCHEDULING.md "InfiniBand pools grow on demand"), so the nodes
boot after `scaling.min` goes to 1 and a start takes the usual few minutes longer than on a pool with nodes up.

Start and stop, no autoscaling in between: `scaling.min` 1 starts the replica group (the nodes boot, the drivers
install, the weights load: 10-20 minutes for a trillion-parameter model), 0 stops it;
`PATCH /v1/endpoints/{id} {"scaling": {"min": 1}}` does that. `scaling.idle_s` stops it after that many seconds
without a request, measured by the API's reconcile loop from the later of the last authorized request (the
gateway's authorize call stamps the LeaderWorkerSet in every region of the model) and the moment the leader became Ready; the stop is a normal definition
write (history entry by `idle-shutdown`). A call to a stopped or starting multi-node endpoint gets 503 with that
explanation. The Service and the gateway route of the leader carry a KServe predictor's name
(`<id>-predictor.models.<domain>`), so authorization, the certificate, LiteLLM and `:invoke` are the same as for
a one-pod endpoint.

KServe's `LLMInferenceService` (the llm-d integration; multi-node on a LeaderWorkerSet, prefill/decode
disaggregation, KV-cache-aware routing, Workload Variant Autoscaler) was evaluated for this path and is
not used. It is a separate KServe install (`kserve-llmisvc-crd`, `kserve-llmisvc-resources` and the runtime
configs, not in the fleet) and brings the Gateway API Inference Extension (an InferencePool and an endpoint
picker per service), Envoy AI Gateway, and for scaling WVA with a Prometheus Adapter or KEDA (scale-to-zero only
through KEDA); its LeaderWorkerSet size follows `parallelism.data / dataLocal` and its HTTPRoute and Gateway
are its own, so the variant routing, the authorizer on the predictor route, the fleet certificate and the
request-based idle shutdown above would each need a second implementation. The rendered LeaderWorkerSet
serves the same vLLM recipes with one object and no further controllers; the LLM-specific features of
`LLMInferenceService` are the reason to revisit it.

Start-up time: every endpoint (both kinds) reports `startup_s`, `started_at` and `ready_at` of its newest pod
(`GET /v1/endpoints`): pod created to Ready, which includes a cold node's boot and driver install, the image pull
and the model load; the Grafana dashboard "Endpoints" shows it as a table by model.
